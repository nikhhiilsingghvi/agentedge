STAGE 0 Startup & Init once

All components are instantiated once before the loop begins. No API calls or sensor reads occur here.

SensorSimulator — 5 virtual sensors: mpu6050, dht22, ina219, hcsr04, mq135
ActuatorSimulator — 6 actuators: relay, buzzer, led_red, led_grn, led_yel, ble
ResourceMonitor — wraps psutil; reads real host RAM/CPU each step
RecoveryProtocol — loads failure taxonomy & sensor criticality matrix
LLMPlanner — connects to Gemini / Anthropic / Ollama based on config
Executor — holds refs to actuator sim & resource monitor
AgentEventLogger — opens session log file in logs/
# main.py → run_demo() loop = AgentLoop() # one-time init loop.run(max_cycles=3) # 3 cycles
PHASE 1 Perceive <1 ms

All 5 sensors are read simultaneously. Successful readings are cached as "last known good" for use in future recovery.

Calls sensor_sim.read_all() — triggers all 5 read methods
Each sensor internally evolves machine state: NORMAL → DEGRADING → FAULT (time-based)
~5% random chance per sensor of returning a FAILED reading (SIM_SENSOR_FAILURE_PROB)
Every non-failed value stored via recovery.update_last_known_good()
# Returns Dict[sensor_id, SensorReading] readings = sensor_sim.read_all() # keys: mpu6050, dht22, ina219, hcsr04, mq135 failures = {sid: r for sid, r in readings.items() if r.is_failed}
PHASE 2 Recover ~103 ms if triggered

Skipped entirely if no failures detected. Otherwise, the hierarchical recovery matrix selects an action per failed sensor based on criticality level.

classify_failure(reason) → maps error string to TIMEOUT / BAD_DATA / DISCONNECT / BUS_ERROR
CRITICAL sensors (mpu6050, ina219) → RETRY up to 3×; abort if all fail
HIGH sensor (dht22) → RETRY; fallback to SUBSTITUTE last known good value
MEDIUM sensors (hcsr04, mq135) → SKIP; task continues without them
Recovered value is patched back in-place: readings[sid].value = recovered_value
# Novel Contribution #2 record = recovery.recover( sensor_id="mpu6050", failure_reason=reading.failure_reason, read_fn=lambda: sensor_sim.read_vibration() ) # → RecoveryRecord(outcome, recovered_value)
PHASE 3 Plan (LLM) ~2117 ms · 82% of cycle

The SLM receives structured sensor data and produces a JSON action plan. This is the only network-bound operation in the cycle. In hardware mode, TinyLlama / Phi-3-Mini runs fully offline on-device.

format_perception(readings) builds human-readable sensor string sent to the LLM
System prompt defines: thresholds, actuator commands, exact JSON output format
LLM returns { situation, severity, reasoning, steps: [...] }
If JSON parse fails → safe default plan activated: buzzer ON + BLE ALERT CRITICAL
severity must be exactly one of: NORMAL / WARNING / CRITICAL / FAULT
Produces 1–4 PlanStep objects per cycle (action_type, target, command, payload)
# Planner formats sensor data as text "MPU6050: 0.42 g [OK]" "DHT22: 28.5 Celsius [OK]" # → LLM call (Gemini Flash / Anthropic / Ollama) # → parse_plan() → AgentPlan object plan.severity = "FAULT" # e.g. plan.steps = [S1, S2, S3, S4]
PHASE 4 Execute (RAD) ~525 ms

Each plan step is executed one by one. Before every step, the system checks live RAM/CPU. If resources are critical, Novel Contribution #1 (RAD) activates to decompose the step rather than discard it.

Per-step: resource_monitor.check_before_step() samples real psutil RAM/CPU
NORMAL state → execute step as-is with full payload
WARN state → prefer lightweight execution where semantically safe
CRITICAL + decomposable → split into sequential SubStep objects (RAD)
CRITICAL + non-decomposable safety step → DEFERRED (never silently mutated)
relay→OFF automatically calls sensor_sim.inject_recovery(), resetting machine state
# action_type dispatch if step.action_type == "ACTUATOR": actuator_sim.execute(step.target, step.command) elif step.action_type == "ALERT": actuator_sim.execute("ble", "ALERT", payload) # LOG / VERIFY / WAIT handled locally
PHASE 5 Verify <15 ms

Confirms that actuator commands were actually applied. Checks each step's expected post-execution state against the actuator simulator's internal state dictionary — not just sensor delta logging.

Per step: actuator_sim.get_state(target) compared to expected command outcome
Returns structured VerificationResult(step_id, expected, observed, success)
BLE verified via actuator_sim.alert_log — checks that alert was actually recorded
Sensor delta used as secondary evidence — not primary proof of actuator success
Failed verification propagates to CycleRecord.verification_success = False
# For each executed step: expected = "OFF" # relay OFF command observed = actuator_sim.get_state("relay") success = observed == expected # → VerificationResult stored in CycleRecord
POST-LOOP Session Report after all cycles

After all cycles complete (or on Ctrl+C), a structured JSON session report is written to logs/ and a rich summary table is printed to the terminal.

planner_stats — avg_latency_ms, avg_tokens_per_plan, backend, model
executor_stats — total_splits, split_rate_pct, RAD metrics (decomposed, deferred, substeps generated)
resource_stats — ram_avg_percent, cpu_peak_percent, estimated_avg_power_w, total_energy_mj
recovery_stats — total_failures, success_rate_pct, by_failure_type, avg_latency_ms
cycle_records — full CycleRecord per cycle including verification_success, peak_ram_percent, energy_mj
Key architectural insight: The LLM planning phase accounts for 82% of total cycle time (~2117ms of ~2800ms avg). All sensor reads, resource checks, actuator dispatch, and verification complete in under 650ms combined. In hardware mode with on-device TinyLlama / Phi-3-Mini via llama.cpp, the PLAN phase is the primary latency bottleneck to characterise — which is precisely what AgentEdge-Bench Task Category A measures.

Our Three Novel Contributions

Bridging the critical gap between cloud-scale agent theory and physical edge execution.

Novel Contribution 1

#1 Resource-Adaptive Task Decomposition (RAD)

Continuous telemetry monitor tracking RAM (71.6% peak threshold) and CPU throttle. Dynamically decomposes monolithic multi-step plans into atomic single-action execution steps when resource starvation is detected. No existing edge literature implements runtime dynamic decomposition.

Fills gap in:
AutoGenRüb & GerhardsATLASv2Qin et al.
Novel Contribution 2

#2 Sensor Failure Recovery Protocol

Formal fault taxonomy classifying hardware faults into TIMEOUT, BAD_DATA, DISCONNECT, and BUS_ERROR. Coupled with a deterministic RETRY / SKIP / ABORT decision matrix and peripheral reset routines, achieving a verified 50% automated recovery rate on embedded hardware.

Fills gap in:
ReActRüb & GerhardsATLASv2Belcak et al.
Novel Contribution 3

#3 AgentEdge-Bench: 20-Task Benchmark

The first standardized benchmark purpose-built for embedded agentic AI. 20 real hardware scenarios spanning 4 task categories (Nominal Monitoring, Thermal Threshold, Gas Leak Alert, Sensor Degradation) evaluating planning latency, token efficiency, and recovery success.

Fills gap in:
ReActBelcak et al.Rüb & Gerhards
